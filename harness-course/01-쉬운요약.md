# 하네스 엔지니어링, 진짜 쉽게

> 원본 PDF(17강, 226쪽)의 핵심만 추린 버전입니다.
> 각 단계마다 **"이렇게 생각하면 된다(비유)"** 와 **"클로드에게 이렇게 말하면 된다(프롬프트)"** 를 붙였습니다.

---

## 0. 하네스가 뭔데?

**하네스 = 말(馬)에 채우는 마구(고삐·안장).**
말(AI)은 이미 힘이 셉니다. 문제는 **엉뚱한 데로 달린다는 것.**
그래서 고삐를 채워서 **우리가 원하는 방향으로만** 달리게 만드는 게 하네스 엔지니어링입니다.

```
AI 에이전트 = 똑똑한 모델 + 하네스(고삐)
```

하네스는 딱 4가지로 이루어져 있습니다.

| 구성 | 쉬운 말 | 예시 |
|---|---|---|
| 가이드 | "우리 집 규칙은 이거야" | CLAUDE.md, 스킬 |
| 검증 | "규칙 어기면 못 지나가" | 테스트, 자동 검사 |
| 피드백 루프 | "틀렸으면 다시 해" | 테스트 실패 → 수정 |
| 사람 개입점 | "중요한 건 내가 정할게" | 승인 게이트 |

## 어려운 용어 → 쉬운 말 번역표 (수업 중 이걸로 말하세요)

| PDF 용어 | 수업에서 부를 이름 |
|---|---|
| CLAUDE.md | AI용 **신입사원 안내서** |
| Skill (스킬) | AI에게 주는 **레시피 카드** (/명령어로 꺼내 씀) |
| Agent (에이전트) | **검사관** (매번 스스로 판단하는 도우미) |
| Hook (훅) | **자동 감시카메라** (특정 순간에 자동 실행) |
| husky / lint-staged | **커밋 검문소** |
| commitlint / Conventional Commits | **커밋 메시지 맞춤법 검사** |
| spec-original / spec-fixed | **처음 주문서 / 확정 주문서** |
| PRD | **설계도 한 장** |
| ADR | **"왜 이렇게 정했나" 메모** |
| Out of Scope | **"이번엔 안 만들 것" 목록** |
| 수직 슬라이싱 | **케이크 세로로 자르기** (한 조각에 모든 층) |
| Acceptance Criteria (AC) | **완료 체크리스트** |
| Given-When-Then | **"~일 때 / ~하면 / ~된다"** |
| TDD | **시험 문제 먼저 내고 공부하기** |
| Red / Green / Refactor | **빨간불(틀림) → 초록불(맞음) → 정리정돈** |
| YAGNI | **"안 시킨 건 하지 마"** |
| Stub / Mock | **가짜 부품 / 가짜 상대역** |
| 커버리지 | **시험 범위 중 실제로 풀어본 비율** |
| E2E | **진짜 손님처럼 처음부터 끝까지 써보기** |
| CI | **남의 깨끗한 컴퓨터에서 다시 검사** |
| 브랜치 보호 | **검사 통과 못 하면 합치기 버튼 잠금** |

## 전체 흐름 한 줄

```
규칙 알려주기 → 자동 검문소 → 뭘 만들지 확정 → 설계도 → 작게 쪼개기
→ 시험 문제 먼저 → 통과시키기 → 정리 → 진짜 써보기 → 남의 컴퓨터 검사 → 합치기
```

아래 10단계가 전부입니다.

## 1단계. AI에게 "우리 집 규칙" 알려주기 (CLAUDE.md)

**왜?** 클로드는 **금붕어 기억력**입니다. 대화창을 닫으면 어제 한 말을 다 잊어요.
그래서 매번 자동으로 읽는 **안내서 파일(CLAUDE.md)** 을 만들어 둡니다.

**할 일**
1. `/init` 으로 초안 만들기 (AI가 프로젝트를 훑어보고 자동 작성)
2. 초안을 **사람이 읽고 고치기** ← 그대로 쓰면 안 됨!
3. 200줄 이하로 유지

**클로드에게 이렇게 말하기**
```
/init
```
```
방금 만든 CLAUDE.md를 보강해줘.
- 컴포넌트는 항상 named export로 만든다 (export default 금지)
- 이벤트 함수 이름은 handle로 시작한다 (handleClick)
- 테스트 실행: npm test / 개발 서버: npm run dev
200줄 넘지 않게 해줘.
```

## 2단계. 자주 쓰는 일은 "레시피 카드"로 (Skill)

**왜?** 같은 부탁을 매번 길게 타이핑하면 지치고, 빠뜨립니다.
`.claude/skills/이름/SKILL.md` 에 절차를 적어 두면 `/이름` 한 마디로 실행됩니다.

- 프로젝트 폴더의 `.claude/skills/` → **팀 모두 공유**
- 내 컴퓨터의 `~/.claude/skills/` → **나만 어디서나**

**클로드에게 이렇게 말하기**
```
.claude/skills/mermaid-diagram/SKILL.md 스킬을 만들어줘.
하는 일: src/ 폴더를 훑어서 파일끼리 어떻게 연결되는지
Mermaid 다이어그램으로 docs/architecture/index.html 에 그려서 브라우저로 열기.
```
그다음엔 그냥:
```
/mermaid-diagram
```

## 3단계. 커밋할 때 자동 검문소 (husky + lint-staged + commitlint)

**왜?** "커밋 전에 검사 돌려야지"를 사람은 **반드시 까먹습니다.**
그래서 커밋 버튼을 누르는 순간 **자동으로 검사**하고, 틀리면 **커밋을 막아버립니다.**

- **코드 검사**: 방금 고친 파일만 빠르게 정리·검사
- **메시지 검사**: 커밋 메시지가 `feat: ...`, `fix: ...` 형식인지

| 머리말 | 뜻 |
|---|---|
| feat | 새 기능 |
| fix | 버그 고침 |
| test | 테스트 |
| refactor | 동작은 그대로, 정리만 |
| chore | 설정·잡일 |

**클로드에게 이렇게 말하기**
```
husky, lint-staged, commitlint 설치하고 설정해줘.
- 커밋 전: 바뀐 .ts/.tsx 파일만 eslint --fix, prettier --write
- 커밋 메시지: Conventional Commits 형식 강제
- CLAUDE.md에 커밋 메시지 규칙도 추가해줘
설정 끝나면 일부러 틀린 메시지로 커밋해서 막히는지 보여줘.
```

## 4단계. 뭘 만들지 "AI가 나를 인터뷰" (spec)

**왜?** "태그 기능 만들어줘" 한 마디면 AI가 **제멋대로** 정합니다. (최대 몇 개? 대소문자? 중복?)
잘못 정한 걸 나중에 고치면 **100배** 비쌉니다. 처음에 정하면 1배.

**핵심 요령: 역할을 뒤집어서 AI가 나에게 질문하게 한다.**
- 한 번에 하나씩 질문
- 추천 답도 같이
- 코드 먼저 보고 질문

**결과물**: `spec-original.md`(처음 주문서) + `spec-fixed.md`(확정 주문서)

**클로드에게 이렇게 말하기**
```
docs/features/tag/spec-original.md 를 읽고, 코드베이스를 먼저 살펴본 다음,
구현 전에 확인해야 할 것들을 나한테 질문해줘.
- 한 번에 하나씩만 질문해
- 각 질문마다 너의 추천 답과 이유도 같이 말해줘
인터뷰가 끝나면 결정한 내용과 용어 정의를 spec-fixed.md 로 정리해줘.
```

## 5단계. 디자인 규칙도 글로 적기 (design.md + Hook)

**왜?** 디자인 이미지 한 장만 주면 AI는 매번 색·간격을 **대충 비슷하게** 바꿉니다.
**글로 된 디자인 규칙**을 만들고, **자동 감시카메라(Hook)** 로 지키는지 검사합니다.

- 디자인 규칙 파일: 색 / 글자 / 간격 / 컴포넌트
- Hook: 클로드가 파일을 고칠 때마다 자동으로 규칙 위반 검사

**클로드에게 이렇게 말하기**
```
이 디자인 이미지를 보고 docs/design/ 아래에
colors.md, typography.md, spacing.md, components.md 로 디자인 규칙을 정리해줘.
Tailwind 클래스 이름으로 정확하게 적고, 상태별(기본/hover/비활성/에러)로 나눠줘.
```
```
클로드가 파일을 Edit/Write 할 때마다 scripts/check-design-system.js 가
자동 실행되도록 .claude/settings.json 에 PostToolUse hook 을 걸어줘.
규칙에 없는 색(예: 임의의 hex 색상)을 쓰면 경고를 내게 해줘.
```

## 6단계. 설계도 한 장 + "안 만들 것" 목록 (PRD + ADR + Out of Scope)

**왜?** 궁금한 게 생기면 **여기 한 장만 보면 되는** 문서가 필요합니다.

설계도에 들어갈 5가지:
1. 개요 (뭘, 왜)
2. 사용자 이야기 (사용자는 이렇게 쓴다)
3. **기술 결정 + 이유** (ADR) ← 가장 중요
4. **이번에 안 만들 것** ← 이거 안 적으면 AI가 알아서 만들어버림
5. 용어 정리

**기술 결정 메모(ADR) 4줄**: 상황 / 다른 후보들 / 고른 것 / 그래서 생기는 장단점

> ⚠️ 기술 결정은 **AI가 아니라 사람이** 고릅니다. AI는 팀 사정·일정·앞으로의 계획을 모르니까요.

**클로드에게 이렇게 말하기**
```
spec-fixed.md 로 docs/features/tag/prd.md 를 만들어줘.
기술 결정 섹션은 TODO 로 비워두고,
태그 데이터 저장 방식 3가지 안을 표로 비교해줘
(데이터 구조 / 고칠 곳 / 테스트 쉬움 / 기존 코드와 비슷한 정도 기준).
```
(사람이 하나 고른 뒤)
```
B안으로 결정. 기술 결정 섹션을 상황 / 대안 / 결정 / 결과(장점+단점) 4가지로 써줘.
Out of Scope 에는 "태그 색상 바꾸기, 태그 이름 수정, 태그 자동완성" 을 넣어줘.
```

## 7단계. 일을 "케이크 세로로" 자르기 (이슈 분해)

**왜?** "API 먼저, 화면 나중에" 처럼 **가로로** 자르면, 3개 다 끝나야 겨우 동작합니다.
**세로로** 자르면 이슈 하나만 끝내도 **사용자가 써볼 수 있는 무언가**가 생깁니다.

**판단 질문 하나**: "이것만 끝내면 사용자에게 보여줄 게 있나?" → 예면 OK

**완료 체크리스트(AC)** 는 "~일 때 / ~하면 / ~된다" 로:
```
- [ ] 노트 편집 화면에서, 태그를 입력하고 Enter 를 누르면, 태그가 추가되어 보인다
- [ ] 이미 있는 태그를 입력하면, 중복으로 추가되지 않는다
```

**클로드에게 이렇게 말하기**
```
prd.md 를 보고 기능을 이슈로 쪼개서 docs/features/tag/issues.md 에 써줘.
- 각 이슈는 그것만 끝내도 사용자가 확인할 수 있는 동작이 있어야 해
- 각 이슈에 "~일 때 / ~하면 / ~된다" 형식의 완료 체크리스트를 달아줘
```
```
issues.md 의 이슈들을 gh CLI 로 GitHub Issues 에 등록해줘.
```

> 💡 4~7단계를 매번 하기 귀찮으면 → **`/feature-planner` 스킬로 묶기** (8강).
> 단, "3안 중 고르기 / 안 만들 것 확정 / 쪼갠 이슈 검토" 3군데는 **반드시 사람에게 물어보게** 합니다.

## 8단계. 시험 문제 먼저, 공부는 나중 (TDD)

**왜?** AI한테 "구현해줘" 하면 **코드와 테스트를 동시에** 만듭니다.
그럼 테스트가 **이미 짠 코드를 "맞다"고 도장만 찍어줍니다.** 버그도 같이 통과!

그래서 **순서를 뒤집습니다.**

| 단계 | 신호등 | 하는 일 | 핵심 규칙 |
|---|---|---|---|
| 준비 | - | 함수 모양과 시험 문제 목록 정하기 | 정상 / 경계 / 예외 나누기 |
| Red | 🔴 | 실패하는 테스트 먼저 작성 | "구현이 없어서" 실패해야 함 |
| Green | 🟢 | 테스트 통과하는 **최소한**만 구현 | **안 시킨 건 하지 마 (YAGNI)** |
| 검사관 | 🔍 | 완료 체크리스트를 다 채웠는지 따로 검사 | 테스트 통과 ≠ 완료 |
| Refactor | 🧹 | 동작은 그대로, 코드만 정리 | 하나 고치고 테스트, 깨지면 즉시 되돌리기 |
| 보안 | 🔒 | 타입 검사 + 취약점 검사 | `tsc --noEmit`, `npm audit` |

**경계값이 왜 중요?** `<` 와 `<=` 하나 차이 버그는 **딱 경계에서만** 보입니다.
(태그 최대 5개면 → 4개, 5개, 6개 일 때를 다 시험)

**클로드에게 이렇게 말하기** (스킬로 만들어 두면 `/이름 1` 한 줄)
```
이슈 #1 을 보고 함수 시그니처(입력/출력/에러 메시지)를 먼저 제안해줘. 구현은 하지 마.
그다음 테스트 시나리오를 정상 / 경계 / 예외로 나눠서 목록으로 보여줘.
```
```
[Red] 승인한 시나리오대로 Vitest 테스트를 작성해줘.
구현 코드는 절대 작성하지 말고, 함수는 throw new Error('not implemented') 로만 만들어둬.
npm test 돌려서 "N개 실패, 0개 통과" 인지 보여줘.
```
```
[Green] 실패하는 테스트를 하나씩만 통과시켜줘.
테스트에 없는 기능은 절대 추가하지 마. 테스트 파일은 수정 금지.
하나 통과시킬 때마다 npm test 전체를 돌려서 다른 게 안 깨졌는지 확인해.
```
```
@ac-verifier 이슈 #1 의 완료 체크리스트를 현재 코드와 테스트가 전부 만족하는지
독립적으로 검사해줘. 빠진 게 있으면 목록으로 알려줘.
```
```
[Refactor] 동작은 바꾸지 말고 코드만 정리해줘.
기준: 중복 / 이름 / 너무 많은 일을 하는 함수 / 매직넘버 / CLAUDE.md 규칙.
한 번에 하나씩 고치고 매번 npm test. 깨지면 바로 되돌려.
```
```
/security-review
```

**이슈 하나 끝나면?** 다음 이슈에 **똑같은 순서**를 반복. 처음엔 30분, 두 번째부터 5~10분.

## 9단계. 진짜 손님처럼 써보기 (E2E)

**왜?** 부품(함수)이 다 멀쩡해도 **조립이 잘못되면** 앱은 안 돌아갑니다.
로봇 브라우저(Playwright)가 진짜로 클릭하고 타이핑해봅니다.

**규칙**
- **적게만** 짠다 (느리고 비싸니까). 정상 흐름만.
- 버튼은 **화면에 보이는 이름**으로 찾는다 (`getByRole` → `getByText` 순)
- 테스트가 끝나면 만든 데이터는 **치운다**
- E2E에서 버그를 찾으면 → **E2E를 고치지 말고** 단위 테스트를 추가해서 고친다

**클로드에게 이렇게 말하기**
```
Playwright 를 설치하고 prd.md 의 사용자 이야기대로 tests/tag.spec.ts 를 만들어줘.
- 정상 흐름만, 처음부터 끝까지 한 사용자 여정으로
- 셀렉터는 getByRole > getByText > getByPlaceholder > getByTestId 순서
- afterEach 에서 테스트가 만든 노트를 지워줘
그리고 npm run test:e2e 로 돌려줘.
```

## 10단계. PR → 남의 컴퓨터 검사(CI) → 합치기

**왜?** "내 컴퓨터에선 되는데요?" 는 증거가 안 됩니다.
**GitHub의 깨끗한 컴퓨터**에서 처음부터 다시 설치하고 검사합니다.

검사 4종: 코드 스타일(lint) / 타입(tsc) / 취약점(audit) / 테스트(test)

**브랜치 보호**: CI 통과 못 하면 **합치기 버튼 자체가 잠김** → 사람 의지력 대신 시스템이 강제.

**클로드에게 이렇게 말하기**
```
.github/workflows/ci.yml 을 만들어줘.
main 으로 가는 PR 마다: npm ci → lint → tsc --noEmit → npm audit --audit-level=moderate → npm test
```
```
/create-pr 스킬을 만들어줘.
순서: E2E 실행 → 실패하면 중단하고 원인 안내 → 통과하면 push → gh pr create.
PR 본문에 "Closes #이슈번호" 넣고, 사용자가 "PR 올려줘"라고 해도 이 스킬이 실행되게 해줘.
```

## 한 장 요약 (칠판에 쓸 것)

1. **안내서**를 만든다 — AI는 금붕어니까
2. **검문소**를 세운다 — 사람은 까먹으니까
3. **AI가 나를 인터뷰**하게 한다 — 처음에 정하면 100배 싸니까
4. **안 만들 것**을 적는다 — 안 적으면 AI가 만드니까
5. **케이크를 세로로** 자른다 — 하나만 끝내도 동작하게
6. **시험 문제 먼저** 낸다 — 코드가 시험에 맞추도록
7. **안 시킨 건 안 한다** — 검증 안 된 코드는 빚이니까
8. **남의 컴퓨터**에서 검사한다 — "내 컴에선 됨"은 증거가 아니니까
9. 반복되면 **레시피 카드(스킬)** 로 만든다
10. 중요한 결정은 **사람이** 한다 — AI는 제안자, 사람은 결정자
